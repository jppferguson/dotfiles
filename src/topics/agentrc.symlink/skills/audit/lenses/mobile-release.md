# Lens: mobile app release safety

Read-only review of a native or cross-platform app's release configuration, on-device data and robustness. Do not run builds, simulators or device tools. Another lens covers what data goes to analytics and error reporting; this one owns security, the correctness of what ships in the binary, and what happens to a user's data across updates. For every finding say whether the fix needs a **new store binary** or can ship **over the air**, and check first whether over-the-air updates are actually enabled in the release build: if they are not, nothing is "JavaScript only". When the native projects are generated and not committed, read the config plugins and any local prebuild, and say plainly what could not be verified.

Check:

1. **Release configuration.** Build profiles and what differs between them. Can a development-only setting (dev client, debug menu, test keys, a build flag) reach a production build? Is a missing profile or variant variable handled safely? Values inlined at build time (error-reporting DSN, analytics key): does anything check they are present before a release build, or does a missing one silently switch a feature off for that binary?
2. **Over-the-air updates.** Enabled in the release binary or not; runtime version policy; channel per profile; code signing; rollback when an update fails to launch. Which flags or config an update can change, and whether that lets an update switch on something the store review or privacy labels did not cover.
3. **Permissions and the native manifest.** Requested versus used permissions, usage strings, background modes, entitlements. Backup behaviour for on-device data (Android `allowBackup`, iOS backup exclusion) against any "stays on your device" promise. Cleartext traffic, exported components, URL schemes, and residue from development tooling in the release manifest.
4. **Deep links and routing.** What an external link can make the app do without the user's intent: mutate or reset data, pre-fill text, open a debug screen, bypass a lock. Are route parameters validated? Are test or showcase routes reachable in production?
5. **Lock or privacy screen**, if there is one. Does it fail open or closed on error? Can the user be locked out for good when the device's passcode or biometrics are removed (and is the only way out deleting the app and its data)? Is content visible in the app switcher or recent-apps thumbnail, after a notification tap, or on resume?
6. **On-device storage.** Schema validation and versioned migrations on read. What happens to stored data that fails validation after an update: silently wiped, quarantined, reported? Is there a committed fixture of each shipped stored shape that must keep loading? Write races between screens, and a failed read followed by a write that overwrites good data.
7. **Hidden or debug menus.** How they are gated in production, whether the gate can be met by an unintended device, what the menu can do, and whether enabling it creates a persistent identifier on ordinary users' devices.
8. **Dates and clocks.** Time zones, daylight saving, the midnight rollover while the app is open, a device with the wrong date, travel. Anything meant to be deterministic that reads unseeded randomness or the wall clock.
9. **Local notifications.** Permission flow, the operating system's cap on pending notifications, rescheduling after a data change, time-zone change, reboot and app update, orphaned or duplicate notifications, whether switching them off cancels everything, and what text appears on a lock screen.
10. **Errors and recovery.** Does a render crash that is deterministic from stored data leave the user any way back other than reinstalling? Error-reporting initialisation order and the missing-key case. What native crash reports bypass the JavaScript scrubbing.
11. **Web build and service worker**, if the app also ships to the web: cache versioning, whether a bad deploy can strand users on a stale or broken shell, security headers on the static export.
12. **Dependencies.** Native modules with no importers (verify each with a grep), dormant flag-gated code and its SDK shipped in the binary, pre-release pins.
13. **User text into generated output.** Names or free text interpolated into HTML for print or share: is it escaped, and are generated files left behind in a cache?

Report findings as CRITICAL / HIGH / WARNING, each with `file:line`, a one-line description, the failure chain in terms of what the user does and what happens, a concrete fix naming an existing helper or exemplar in this codebase, **store binary or over the air**, how to verify (the existing test or device flow to extend, checked to exist), and "verified by reading" or "unverified". Report clean areas in one line each. End with a coverage statement listing files not reached and everything that needs a device or a built artefact to confirm.
