# Lens: internal tools, repository scripts and delivery infrastructure

Read-only review of everything that runs on a developer's machine or in CI rather than in the product: local admin or content tools, repository scripts, release and deploy scripts, self-hosted CI runners, and the boundary between coding agents and the machines that review their work. Do not run dev servers, builds or tests, and do not contact any hosted service. The orchestrator reviews workflow permissions, action pinning and dependency automation itself; do not repeat that.

Check:

1. **Local-only tools** (an admin app bound to localhost, a content editor). How it binds (loopback or all interfaces). What its "local only" check actually tests: a check on the socket address is passed by a DNS-rebinding page, and only a `Host` header allow-list stops that. Is every action that writes or runs a command guarded before it reads its arguments, is there a meta-test that fails when a new action forgets the guard, and are **reads** guarded too? If the tool is due to be hosted, what authenticates it then.
2. **File and command surface of those tools.** Paths built from request input versus an allow-list; `..` and symlinks; every `spawn` or `exec` and whether any argument or the command string comes from a request; whether the tool can commit or push; how visible a hostile write would be.
3. **Injection in scripts.** Every shell invocation or string-built command where an argument comes from a branch name, commit subject, file name, task title, environment variable or CLI input. Name the line and the input that breaks it.
4. **Secrets handling.** Scripts that print a secret, pass it on a command line visible in the process list, write it to a file that is not ignored, or store it where any local process can read it without a prompt. Anything that looks like a real credential committed in scripts, workflows, examples or docs (publishable keys are not secrets; say so rather than flagging them).
5. **Self-hosted CI runners.** Persistent or ephemeral; the job user's privileges (sudo, container-runtime group membership is root-equivalent); host mounts and what they expose; network reach to the host and local network; credentials left on disk between jobs. Which jobs holding deploy tokens or acting as a release gate share that runner with jobs that execute untrusted install scripts. Provisioning that downloads unpinned or unverified code. A remote build cache every job can write to, where a cache hit counts as a pass.
6. **Release gates.** Can the promote or deploy step be made to accept a commit whose checks did not pass (a skipped, cancelled or re-run job counted as success; a commit on the wrong branch)? Can the change-detection that decides which jobs run classify a code change as docs-only?
7. **Destructive scripts and their guards.** Can a reset, clean or push ever point at a non-local database or environment? Can a clean-up script delete uncommitted, unpushed or git-ignored local work (ignored files do not show in a porcelain status)?
8. **Locks and queues between parallel agents.** Staleness decided by process ID alone (a reused ID holds the lock for ever), waits with no time limit, a crashed holder blocking everyone.
9. **The agent trust boundary.** What code from an agent's or cloud session's branch executes on a developer machine before a human has read the diff: git hooks that run a script from the checked-out tree, install scripts, and the validation run itself (which executes the branch's tests and config). With whose credentials does it run, and what can it reach? If there is a protected-path list, name the gaps, and say plainly that no path list makes executing branch code safe: only running it without credentials does.
10. **Artefact handling.** Scripts that download build artefacts and overwrite tracked files: path traversal from artefact names, and whether the artefact is checked to belong to the current branch and repository.
11. **Derived versus hand-maintained guard lists.** Secret scanners, client-bundle checks and protected-path lists: is the list of guarded names derived from a source that cannot go stale, and does a test fail when it shrinks?

Report findings as CRITICAL / HIGH / WARNING, each with `file:line`, a one-line description, the failure chain (who, what input or request, what result), a concrete fix naming an existing helper or exemplar in this codebase, how to verify (the existing test file to extend, checked to exist), and "verified by reading" or "unverified". Report clean areas in one line each. End with a coverage statement listing files read in full, files only grepped and files not reached.
